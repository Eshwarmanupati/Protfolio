I build it, then I break it

Most of my coursemates can build a feature. Six months of testing other people’s code taught me to find the ways it falls over first — which is the part that decides whether it survives contact with real users.

Developer + Manual QA 6 months on the job Repro-first reporting
01 — The two hats

The same feature, twice

I write it wanting it to work. Then I come back wanting it to fail. The second pass is where the value is.

Building

Make it work

The optimistic pass. Model the data, write the endpoint, wire the screen, ship the happy path.

  • What is the smallest thing that solves the user’s problem?
  • What shape should the data be so the UI stays simple?
  • Which states does the screen actually need?
  • Does it read clearly enough for someone else to review?
then
Breaking

Make it fail

The adversarial pass. Same feature, but now I am looking for the input nobody demoed.

  • What happens on empty, on one item, on two thousand?
  • What if the network dies halfway through the request?
  • What if the same button is pressed twice, fast?
  • What does a user see when it breaks — a message, or a blank screen?

Why a checklist and not just care

Care does not survive a deadline. A list does. The same three things break every project — empty states, double submits and the error path nobody rendered — so I stopped trusting myself to remember them.

What this changed in my code

Smaller units, because a big one is hard to test. Explicit states instead of implicit ones. And error messages written for the person reading them, not for the log file.

Where I want to take it

Manual testing is where I started, not where I am stopping. Automation next — Selenium and API test suites — so the regression pass runs without me.
